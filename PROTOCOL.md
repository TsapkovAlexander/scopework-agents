# Протокол агентов Scopework

Что агенты читают на вашем сервере, что отправляют платформе и что могут от
неё получить. Документ сверяется с кодом механически: список видов команд — с
константой `CommandKinds` (`apps/deploy-agent/internal/agent/localpolicy.go`) и
ветками `RunTask` (`internal/agent/export.go`), поля такта — с JSON-тегами
`TickRequest` (`internal/agent/client.go`), поля снимка агента мониторинга — с
`build-snapshot-json.py`. Разошёлся с кодом — сборка экспорта красная.

На сервере работают два независимых агента:

- **агент развёртывания** — бинарь на Go (`apps/deploy-agent`), служба
  `tracedocs-deploy`, пользователь `tracedocs-agent` (или `root`, если прокси
  сокета Docker не поднялся — установщик говорит об этом вслух);
- **агент мониторинга** — скрипты `push.sh`, `build-snapshot-json.py`,
  `uninstall.sh` в `/opt/tracedocs/monitor`, запуск по cron.

Оба соединяются с платформой сами, по HTTPS. Входящих портов агенты не
открывают.

## Локальная политика сервера

Файл `/etc/tracedocs/agent-policy.conf` — `root:root 0644`, каталог
`/etc/tracedocs` — `root 0755`. Пишет его только root на сервере
(`install.sh --mode …` или правка руками); платформа его изменить не может, и
оба агента только читают. Формат `ключ=значение`, до 4 КБ:

| Ключ | Значения | Нет ключа |
|---|---|---|
| `version` | `1` | файл негоден |
| `mode` | `observe` \| `deploy` | `observe` |
| `commands` | виды команд через запятую (список ниже) | при `deploy` — все виды, при `observe` — ни одного |
| `deploy_agent_updates` | `manual` \| `no_major` \| `auto` \| `pinned X.Y.Z` | `manual` |
| `monitor_agent_updates` | `manual` \| `no_major` \| `auto` \| `pinned X.Y.Z` | `manual` |
| `container_logs` | `allow` \| `deny` | `deny` |

Правила обновлений: `manual` — агент сам не обновляется; `no_major` — сам,
но только в пределах своего MAJOR, смена MAJOR — повторной установкой;
`auto` — на любую цель платформы; `pinned X.Y.Z` — только на эту версию и
только вверх. Команда подключения из интерфейса передаёт `--updates` с режимом
сервера или компании (по умолчанию `no_major`); `install.sh` без `--updates`
оставляет `manual`.

Файла нет — прежнее поведение. Файл негоден (синтаксис, размер, права,
владелец, запись в каталог не только у root) — закрыто всё: `observe`,
`manual`, `deny`, и ошибка уходит в доклад.

Без вшитых ключей выпуска подпись обновления проверить нечем, а бинарь или
бандл, который политику не читает, снял бы её целиком. Поэтому, пока ключей
нет, файл политики ограничивает и обновления:

- `pinned X.Y.Z` исполняется как `manual` всегда: без подписи прийти может что
  угодно ровно под закреплённым номером;
- `no_major` исполняется как `manual` всегда по той же причине: граница MAJOR —
  тоже номер, и смена поведения придёт под следующей минорной;
- `auto` исполняется как `manual`, если файл хоть что-то ограничивает: `observe`
  или `commands` без какого-либо вида из списка ниже; для агента мониторинга —
  ещё и `container_logs` не `allow` (нет ключа — это `deny`), потому что запрет
  логов исполняет сам этот агент;
- `auto` при `deploy` со всеми видами (а у агента мониторинга ещё и с
  `container_logs=allow`) остаётся `auto`: обновление не открывает ничего, что
  файл уже не разрешил.

Что агент развёртывания решил на деле, видно в докладе
(`deployAgentUpdatesEffective`) и в `scopework-agent policy show`.

Посмотреть, что агент понял из файла: `scopework-agent policy show`.

## Виды команд — закрытый список

Агент развёртывания исполняет только эти виды. Всё прочее он отвергает, не
глядя на ответ платформы. В `observe` не исполняется ни один.

<!-- gate:command-kinds -->
- `apply` — привести приложения к желаемому состоянию: файлы, `docker compose up`, прокси Caddy.
- `backup` — снять копию томов и баз приложения по его описанию копий.
- `restore` — развернуть приложение из набора копий.
- `export` — снять слепок стека (compose, `.env`, тома) для переноса.
- `migrate-data` — перенести данные тома в новый стек.
- `start-stack` — запустить остановленный стек.
- `stop-stack` — остановить стек, не удаляя данных.
- `inventory` — осмотреть сервер: контейнеры, стеки, занятые порты.
<!-- /gate:command-kinds -->

Самообновление агента — не команда из этого списка: его решает ключ
`deploy_agent_updates`. Если в агент вшиты ключи выпуска
(`scopework-agent version --trust`), бинарь без годной подписи одним из них он
не ставит; без вшитых ключей подпись не проверяется, и это видно в той же
команде и в докладе `trust`.

## Агент развёртывания

### Что читает на сервере

| Путь | Зачем |
|---|---|
| `/etc/tracedocs/agent-policy.conf` | локальная политика (только чтение) |
| `/etc/tracedocs/deploy/` | личность агента (`agent.key`), состояние, журнал команд `journal.log` |
| `/opt/tracedocs/deploy/` | рабочий каталог: описания стеков, `.env` приложений, клоны репозиториев, копии |
| `/run/tracedocs/docker-proxy.sock` | Docker — через прокси сокета с белым списком запросов; в `observe` прокси пропускает только `GET` и `HEAD`; в любом режиме отклоняет API Docker старше 1.24, `start` контейнера с телом и путь не в каноническом виде. Отсюда требование к хосту: демон Docker с API не ниже 1.24 (Docker 1.12 и новее); `install.sh` версию не проверяет, но требует `docker compose` v2, которого на более старых демонах нет |
| `/proc/loadavg`, `/proc/meminfo`, `/proc/stat`, `/proc/uptime`, `/proc/net/dev`, `statfs` точек монтирования | метрики сервера |
| вывод `sshd -T`, состояние fail2ban | защищённость входа по SSH |
| `/var/log/auth.log` или `/var/log/secure` | неудачные входы по SSH (счётчики и адреса) |
| access-log Caddy, который агент сам и держит | трафик опубликованных приложений (агрегаты по доменам) |
| `/proc/<pid>/cgroup`, файлы cgroup v2 контейнера в `/sys/fs/cgroup` (`memory.current`, `memory.max`, `memory.events`, `cpu.stat`, `pids.current`) | память, CPU, OOM и число процессов контейнеров (секция `workloads`) |
| `/proc/<pid>/net/tcp`, `/proc/<pid>/net/tcp6` процесса контейнера | установленные соединения из сети контейнера: счётчики и внутренние пиры (секция `workloads`) |
| `/proc/self/mountinfo`, `statfs` каталогов томов Docker | занятое место на томах (секция `workloads`) |

Домашние каталоги, чужие файлы и содержимое томов вне задач копии и переноса
агент не читает.

### Что отправляет: такт

Раз в 5–60 секунд агент шлёт `POST /api/deploy/agent/tick`, тело подписано
ключом сервера (Ed25519, ключ создаётся на сервере при установке и его не
покидает). Поля тела:

<!-- gate:tick-fields -->
| Поле | Что это |
|---|---|
| `agentVersion` | версия агента |
| `proxyError` | ошибка прокси сокета Docker; пустая строка — ошибки нет |
| `privilegeMode` | `proxy` — агент от своего пользователя через прокси, `root` — root-эквивалентен |
| `health` | состояние контейнеров опубликованных приложений |
| `presence` | какие стеки платформы есть на диске |
| `traffic` | агрегаты access-log по доменам: запросы, коды ответа, объём |
| `threat` | счётчики подозрительных запросов и неудачных входов по SSH |
| `metrics` | нагрузка, память, диски, сеть, время работы |
| `posture` | вход по паролю и root по SSH, работает ли fail2ban |
| `checks` | доступность опубликованных доменов, проверенная с самого сервера |
| `holdSeconds` | сколько платформе держать ответ, если работы нет |
| `storageKeyAck` | отпечаток ключа хранилища копий, принятого агентом |
| `storage` | исход пробы хранилища копий |
| `report` | номер такта, квитанции и сигналы дрейфа |
| `localPolicy` | локальная политика, как её понял агент, и её ошибка |
| `localJournal` | голова локального журнала команд и последние записи |
| `trust` | отпечатки вшитых ключей выпуска и корней подписи состояния, версия прокси |
| `workloads` | контейнеры и тома: состояние, перезапуски, код выхода, OOM, память, CPU и процессы из cgroup, образ против эталона выпуска, соединения; пятиминутные корзины и события контейнеров. Пиры — только внутренние адреса (частные сети RFC 1918, петля, link-local, общие адреса RFC 6598), внешние соединения идут одним числом |
| `protocol` | что агент исполняет и проверяет: версии содержимого (`content`, сейчас `host-state/0`) и обёртки подписи (`envelopes`: `dsse-ed25519/1`, если вшиты корни подписи состояния, иначе пусто) |
| `signing` | итог проверки подписанного состояния из прошлого ответа: `status` (`accepted`, `refused`, `held` — пакета не было), `reason`, `seq`, `lastAcceptedSeq`, `at`; только у агента с вшитыми корнями |
<!-- /gate:tick-fields -->

Кроме такта агент обращается к `/api/deploy/agent/enroll` (однократная
регистрация по токену из команды установки), `/api/deploy/agent/report`,
`/inventory`, `/migration`, `/registry-login` (итоги заданий и учётные данные
реестра образов для `docker login`) и `/api/deploy/agent-binary` (новый бинарь
при самообновлении). Прежние ручки `/heartbeat`, `/state`, `/health`,
`/presence`, `/traffic`, `/threats`, `/snapshot` — путь отката на старую
платформу, с теми же данными, что и такт; `/state` несёт те же `protocol` и
`signing`.

### Что может получить

Ответ такта несёт желаемое состояние (`apps`, `registries`, `denyIps`,
`platformSubdomainBase`, `objectStorage`), одно задание (`task`: `id`, `kind`
из списка выше, `project`, `dir`, `volume`, `backupSet`), целевую версию агента
и время следующего такта. Приложение в желаемом состоянии — это compose,
`.env`, файлы, домены, источник сборки (git или образ) и описание копий; всё
это исполняется только видами команд из закрытого списка и только если их
разрешает локальная политика.

Агенту с вшитыми корнями подписи состояния (`apps/deploy-agent/trust/state`,
`scopework-agent version --trust`) желаемое состояние приходит подписанным
пакетом `signedState`: подписанное содержимое без значений секретов (в нём
только ссылки на секреты — какие имена ждать) и сами значения рядом. Значение,
на которое подписанное содержимое не ссылается, и недостающее — отказ. Такой агент применяет только пакет, прошедший
проверку подписи и номера; плоские поля состояния в ответе он не применяет,
даже если они пришли. Пакета нет — `stateWithheld` называет причину. Не принял
пакет — состояние не применяется, итог уходит полем `signing` следующего
запроса. Без вшитых корней агент читает плоские поля, как раньше.

### Локальный журнал команд

`/etc/tracedocs/deploy/journal.log` — JSON Lines, владелец — пользователь
агента, `0600`, атрибут `chattr +a`: агент дописывает, но ни усечь, ни
переписать, ни удалить файл не может. Каждая строка:

```
{"v":1,"seq":N,"at":"<UTC>","type":"receive|result|policy|genesis","kind":"desired_state|host_task|self_update","hash":"<sha256 команды>","summary":{…},"decision":"accepted|refused","reason":"…","prev":"<sha256 предыдущей строки>"}
```

`prev` — sha256 байтов предыдущей строки без перевода строки; у первой строки
(`genesis`) пусто. Проверка цепочки без нашего бинаря:

```sh
prev=""
while IFS= read -r line; do
  got="$(printf '%s' "$line" | jq -r .prev)"
  [ "$got" = "$prev" ] || { echo "цепочка разорвана: $(printf '%s' "$line" | jq -r .seq)"; break; }
  prev="$(printf '%s' "$line" | sha256sum | cut -d' ' -f1)"
done < /etc/tracedocs/deploy/journal.log
```

Тем же бинарём: `scopework-agent journal verify` и `scopework-agent journal show`.
Каждая строка журнала дублируется в journald (`journalctl -u tracedocs-deploy`),
куда пишет root.

## Агент мониторинга

### Что читает на сервере

| Путь | Зачем |
|---|---|
| `/etc/tracedocs/agent-policy.conf` | ключи `monitor_agent_updates` и `container_logs` |
| `/opt/tracedocs/monitor/config.env` | адрес приёма и токен сервера |
| `/proc/loadavg`, `/proc/meminfo`, `/proc/stat`, `/proc/uptime`, `/proc/net/dev`, `df` | метрики |
| `docker ps`, `docker inspect`, `docker events` (если Docker есть) | состояние и события контейнеров |
| `docker logs` | хвосты логов контейнеров — только когда их разрешают (раздел «Что может получить») |
| `/var/log/auth.log`, `/var/log/nginx/access.log`, `/var/log/traefik/access.log` и пути из настроек | счётчики угроз |
| вывод `sshd -T`, состояние fail2ban | защищённость входа по SSH |

### Что отправляет

Снимок раз в интервал cron, `POST` на адрес из `config.env`, тело подписано
HMAC (`X-Scopework-Signature`, `X-Scopework-Timestamp`). Поля снимка:

<!-- gate:snapshot-fields -->
| Поле | Что это |
|---|---|
| `schema_version` | версия формата снимка |
| `host_id` | имя сервера |
| `recorded_at` | время снимка, UTC |
| `metrics` | нагрузка, память, диски, сеть, контейнеры, время работы |
| `checks` | проверки доступности адресов из настроек |
| `agent_version` | версия скриптов агента |
| `threats` | счётчики угроз |
| `host_posture` | вход по паролю и root по SSH, fail2ban |
| `container_events` | перезапуски и падения контейнеров |
<!-- /gate:snapshot-fields -->

### Что может получить

Только заголовки ответа: `X-Scopework-Agent-Version` (есть новая версия),
`X-Scopework-Agent-Signature` (подпись бандла) и `X-Scopework-Container-Logs`
(просьба присылать хвосты логов). Если файл политики есть, обновление
ставится только с разрешения `monitor_agent_updates`, а хвосты логов уходят
только при `container_logs=allow`; без файла решают заголовки, как до появления
политики. Если в `push.sh` есть ключи выпуска, бандл без годной подписи не
ставится. Команд агент мониторинга не исполняет.
